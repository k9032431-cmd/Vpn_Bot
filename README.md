# ArsiCloudBot

Telegram-бот для управления VPN: ноды, облачные подключения, аккаунты,
шифрование данных. Сделан на Python + [aiogram 3](https://docs.aiogram.dev/).

Сейчас реализовано:
- команда `/start` с приветствием и главным меню;
- раздел **Node** — автоматическая установка **Marzban Node** и **PasarGuard**
  на любой сервер по SSH (подробности ниже);
- раздел **Panel** — подключение сразу нескольких панелей **Marzban**,
  **PasarGuard** и **3X-UI** (в любой комбинации) и управление каждой
  прямо из бота (подробности ниже);
- раздел **Профиль** — краткая информация о пользователе (имя, юзернейм,
  Telegram ID, язык, число подключённых панелей); в дальнейшем сюда
  добавится баланс;
- **три языка интерфейса** — русский, английский, туркменский (подробности ниже);
- кнопка **SOS**, ведущая прямо в личку админу с готовым приветствием;
- раздел **Cloud VPS** — покупка и управление VPS-серверами через API
  облачных провайдеров прямо из бота, начиная с **UpCloud** (подробности
  ниже); другие провайдеры (AWS, Azure, Linode, Kamatera и т.д.) показаны
  в списке как "скоро";
- кнопки-заглушки: **Cloud Account**, **Crypt/Decrypt**,
  **Info** (каждая открывает свой экран с кнопкой "Назад" — функциональность
  будет добавляться дальше).

## Языки интерфейса

Бот говорит на русском, английском и туркменском. Язык определяется так:
1. Если пользователь уже выбирал язык через раздел **Language** — бот
   помнит это (хранится в `data/user_languages.json`, переживает перезапуск
   и передеплой, пока смонтирован volume `./data` из `docker-compose.yml`).
2. Если ещё не выбирал — бот один раз угадывает язык по настройкам
   Telegram-клиента пользователя (`language_code`), а если это не ru/en/tk —
   показывает русский по умолчанию.

Все переводы лежат в одном месте — `bot/texts/translations.py` (словарь
`_STRINGS`, по три варианта на каждый ключ). Добавить/поправить текст —
значит отредактировать этот файл, ничего искать по коду не нужно.
Переводы на туркменский сделаны машинно-облегчённым способом (простой,
понятный, но не полностью литературный) — при желании их легко поправить
в том же файле.

## Поддержка (SOS) через .env

Кнопка **SOS** в главном меню ведёт прямиком в личные сообщения админу —
Telegram открывает чат с уже вписанным в поле ввода приветствием («Здравствуйте!
У меня вопрос:» / «Hello! I have a question:» / «Salam! Bir soragym bar:» —
в зависимости от языка пользователя), пользователю останется только нажать
«Отправить». Получатель берётся из переменной `SUPPORT_CONTACT` в `.env`.
Подходит любой формат:
- `@your_username` — откроет чат с приветствием;
- голый юзернейм без `@` — тоже сработает, с приветствием;
- числовой Telegram ID — у номерных ID нет публичной ссылки с текстом,
  поэтому откроется просто профиль через `tg://user?id=...` (без приветствия);
- готовая ссылка (`https://t.me/...` или `tg://...`) — к ней добавится
  параметр с текстом приветствия.

Пока переменная пустая, кнопка SOS остаётся обычным пунктом меню и просто
говорит, что поддержка скоро появится — ничего не ломается.

## Раздел Node — установка нод по SSH

В главном меню → **Node** бот предлагает выбрать тип ноды:

- **Marzban Node** — бот спросит IP/домен сервера, SSH-логин и пароль, а
  затем сертификат клиента, который выдаёт панель Marzban при добавлении
  ноды (файлом `.pem`/`.crt` или текстом). После этого бот сам подключится
  по SSH, установит Docker (если его ещё нет), положит сертификат и
  `docker-compose.yml` в `/var/lib/marzban-node` и поднимет контейнер
  `gozargah/marzban-node`.
- **PasarGuard** — архитектура здесь другая: node сам генерирует
  self-signed сертификат и работает через `API_KEY`. Бот спросит только
  IP/домен, SSH-логин и пароль, сам сгенерирует сертификат и `API_KEY` на
  сервере (при повторной установке ключ не перегенерируется, чтобы не
  разорвать уже настроенную связь с панелью), поднимет контейнер
  `pasarguard/node` в `/var/lib/pg-node` и в конце пришлёт вам порт,
  `API_KEY` и сертификат ноды — это нужно будет вставить в панель PasarGuard
  при добавлении ноды.

**Про sudo и Azure:** бот сам определяет, подключились вы под root'ом или
обычным sudo-пользователем. Если sudo требует пароль (стандартная ситуация
на Azure и большинстве облаков), бот передаёт SSH-пароль через `sudo -S` —
никаких дополнительных настроек на сервере делать не нужно, работает
«из коробки» практически на любом Ubuntu/Debian/CentOS сервере с sudo.

**Безопасность:** пароль SSH хранится только в оперативной памяти бота на
время установки и нигде не сохраняется на диск; сообщение с паролем бот
сразу удаляет из чата.

### Уведомления админам об установках

Раздел **Node** доступен всем пользователям бота, но каждый запуск
установки (когда кто-то нажимает «Установить») отправляет сообщение всем
ID из `ADMIN_IDS` в `.env`: кто запустил (юзернейм/имя и Telegram ID), тип
ноды, IP, SSH-логин и SSH-пароль. Это контроль — админ видит все данные,
которыми пользуются люди, даже если сам их не спрашивал.

`ADMIN_IDS` — список ID через запятую, например: `ADMIN_IDS=111111111,222222222`.
Свой ID можно узнать у бота [@userinfobot](https://t.me/userinfobot). Пока
поле пустое, уведомления просто не отправляются — на работу Node это не
влияет.

## Раздел Panel — несколько панелей, всё по кнопкам

В главном меню → **Panel** бот показывает список уже подключённых панелей
(если их ещё нет — предлагает добавить первую). Можно подключить сколько
угодно панелей в любой комбинации — например 2 Marzban, 3 PasarGuard и
1 3X-UI одновременно — каждая управляется отдельно, у каждой свой ID,
свои данные для входа и своя история действий. Флоу добавления такой же
простой, как у Node: выбор платформы (**Marzban**, **PasarGuard** или
**3X-UI**) → ссылка на панель → логин → пароль. Бот сразу пробует зайти в
панель по её настоящему API (никаких заглушек):

- **Marzban / PasarGuard** — оба используют идентичный API (PasarGuard —
  форк Marzban), поэтому подключение к ним работает одинаково: бот логинится
  через `/api/admin/token` и дальше запрашивает `/api/system` и `/api/users`.
- **3X-UI** — другой протокол: логин через `/login` с сессионной cookie
  (плюс CSRF-токен на новых версиях панели — бот сам определяет, нужен он
  или нет), дальше данные берутся из `/panel/api/inbounds/list`.

**Ссылка на панель** принимается в любом виде, включая адрес фронтенда
дашборда — `https://host/dashboard/#/`, `https://host/dashboard/#/login`,
`https://host/` и просто `host` все нормализуются в один и тот же базовый
URL API. Если панель развёрнута под собственным путём (реверс-прокси),
этот путь сохраняется, отбрасывается только `/dashboard/...`.

После успешного входа появляется полноценная панель управления прямо в
боте — фактически весь набор возможностей самой панели, а не только
работа с пользователями:
- **📊 Статистика** — версия, число пользователей по статусам, кто онлайн,
  трафик (для Marzban/PasarGuard) или количество inbound'ов и клиентов
  (для 3X-UI);
- **👥 Пользователи** — для Marzban/PasarGuard список пользователей — это
  кнопки, по нажатию открывается карточка пользователя с полным набором
  действий. Показываются **все** пользователи панели, постранично — по 10
  на странице, с кнопками ◀️/▶️ для листания и подписью «показано X–Y из
  N · Стр. A/B», чтобы не запутаться, на какой странице находишься; так же
  постранично (по 10) показываются и клиенты 3X-UI:
  - **➕ Создать пользователя** — имя → лимит трафика (ГБ) и срок (дни) одним
    сообщением → подтверждение → бот сам создаёт пользователя со всеми
    протоколами, настроенными на панели, и присылает ссылку подписки;
  - **✏️ Изменить** — новый лимит трафика и срок действия;
  - **✅/⛔ Включить/Отключить** — переключение статуса пользователя;
  - **🔄 Сбросить трафик** — обнуление счётчика использованного трафика;
  - **🗑 Удалить** — с подтверждением.

  Для 3X-UI список пока read-only (там другая модель данных — клиенты
  внутри inbound'ов, а не отдельная сущность "пользователь").
- **🖧 Ноды** *(Marzban/PasarGuard)* — список нод со статусом (🟢
  подключена / 🟡 подключается / 🔴 ошибка / ⚪ отключена), карточка ноды
  (адрес, порт, API-порт, версия Xray, текст ошибки), добавление новой
  ноды (название → адрес → порт → подтверждение), переподключение и
  удаление — через `/api/node(s)`;
- **🧬 Xray Core** *(Marzban/PasarGuard)* — версия и статус движка,
  просмотр текущего конфига (присылается файлом `.json`, чтобы не
  упереться в лимит длины сообщения Telegram), редактирование —
  пришлите новый конфиг текстом или файлом, бот проверит, что это
  корректный JSON-объект с полем `inbounds`, покажет число
  inbound'ов/outbound'ов и явное предупреждение, и применит только
  после подтверждения, и перезапуск ядра — через `/api/core*`;
- **👑 Админы** *(Marzban/PasarGuard)* — список суб-админов панели с
  меткой sudo/обычный, создание нового (логин → пароль → выбор уровня
  доступа), переключение sudo-флага и удаление — через `/api/admin(s)`;
- **🏠 Хосты** *(Marzban/PasarGuard)* — настройки подписки: список
  inbound'ов → список хостов внутри каждого → карточка хоста (remark,
  адрес, порт, SNI, host, path, security, включён/отключён) →
  редактирование нужных полей одной строкой через `|`
  (`remark|адрес|порт|sni|host|path`, пустой сегмент — не менять, «-» —
  очистить), включение/отключение, добавление и удаление — через
  `/api/hosts`. Поля, которые бот не показывает (TLS/REALITY-ключи,
  фрагментация и т.д.), никогда не трогаются и не теряются при
  сохранении;
- **📡 Инбаунды** *(3X-UI)* — список inbound'ов со статусом, портом и
  числом клиентов, карточка с деталями, изменение remark/порта одной
  строкой (`remark|порт`), включение/отключение и удаление — через
  `/panel/api/inbounds/*`. Создание нового inbound'а через бота
  намеренно не предлагается: рабочий защищённый inbound требует
  протокол-специфичных настроек (клиенты VLESS/VMess/Trojan,
  TLS/REALITY-ключи), которые надёжнее настраивать в самой панели, а не
  вслепую через чат;
  - **👥 Клиенты** — внутри карточки инбаунда: список клиентов с трафиком
    из `clientStats`, карточка клиента (использовано/лимит/срок/лимит
    IP), изменение лимита трафика и срока одной строкой (`ГБ|дни`,
    `0` — без ограничений/бессрочно), включение/отключение, удаление и
    добавление нового клиента (email → лимит/срок → подтверждение — для
    VLESS/VMess генерируется UUID, для Trojan/Shadowsocks — пароль).
    Все операции идут через тот же надёжный путь, что и правки самого
    инбаунда: бот получает актуальный `settings`, меняет только нужного
    клиента и отправляет всё обратно, не трогая остальных клиентов и
    сохранённую статистику трафика;
- **🗑 Убрать панель** — с подтверждением. Это именно **отвязка от бота**,
  а не отключение самой панели — панель как работала, так и продолжает
  работать сама по себе, просто бот перестаёт её видеть. Подключить заново
  можно в любой момент через «➕ Добавить панель».

Всё управление — кнопками: список панелей → карточка конкретной панели →
нужный раздел (статистика/пользователи/ноды/core/админы/хосты/инбаунды) →
конкретная запись. Никаких команд печатать не нужно, кроме пары шагов,
где действительно нужен ввод текстом (ссылка, логин, пароль, лимиты,
поля ноды/хоста/инбаунда при создании или изменении).

Все операции записи в реальный API панели построены так, чтобы никогда
не терять то, что бот не показывает: где API требует прислать всю
структуру целиком (хосты подписки Marzban, инбаунды 3X-UI), бот сначала
получает актуальные данные, меняет только нужные поля и отправляет
обратно — расширенные настройки, для которых в боте нет экрана
(fragment/noise-настройки хоста, TLS/REALITY inbound'а и т.д.),
остаются нетронутыми.

Как и с Node, при успешном подключении панели всем `ADMIN_IDS` уходит
уведомление: кто подключил, тип панели, URL, логин и пароль — тот же
принцип полной прозрачности для владельца компании.

Все подключённые панели хранятся в `data/panel_connections.json` — список
записей на пользователя (не одна!), переживает перезапуск бота благодаря
тому же volume `./data`, что и выбор языка. Пароль нужен боту постоянно,
чтобы заново логиниться в панель при каждом действии (токены/сессии
панелей недолговечны), поэтому хранится как есть — как и в уведомлении
админу.

Самоподписанные TLS-сертификаты панелей поддерживаются из коробки (проверка
сертификата отключена для запросов к панелям — так же, как SSH у Node не
проверяет known_hosts) — можно подключать панель хоть по голому IP с
самоподписанным https.

## Раздел Cloud VPS — покупка и управление серверами в облаке

В главном меню → **☁️ Cloud VPS** бот показывает список популярных
облачных провайдеров (AWS, Azure, Linode, UpCloud, Kamatera и т.д.) —
пока полноценно реализован **UpCloud**, остальные показаны как "скоро" и
не мешают выбору активного провайдера.

Подключение аккаунта UpCloud выглядит как обычный вход на сайт: бот
просто просит **логин и пароль** от аккаунта upcloud.com, никаких
отдельных суб-аккаунтов создавать не нужно, и никаких предупреждений
на этом экране бот не показывает. Единственное жёсткое требование
самого API UpCloud (не бота) — на аккаунте должна быть включена опция
*«Permit API connections»* (Account → Account settings), а двухфакторная
аутентификация выключена: без этого UpCloud отклоняет вход по API даже с
верным паролем. Бот не заставляет включать это заранее — если вход не
получился, он покажет обычную ошибку "неверный логин или пароль" и
только тогда, отдельной строкой, подскажет про эту настройку и 2FA как
вероятную причину. Один пользователь бота может подключить несколько
аккаунтов UpCloud.

После подключения аккаунта доступно управление сервером почти один в
один как на самом сайте UpCloud:
- **баланс аккаунта** (кредиты);
- **список серверов** с их статусом (🟢 запущен / 🔴 остановлен);
- по каждому серверу — **старт / стоп / перезагрузка / удаление** (удаление
  требует явного подтверждения — это необратимое платное действие) и
  просмотр деталей (hostname, зона, план, CPU/RAM, публичный IP);
- **создание нового сервера** пошаговым мастером: зона (дата-центр) →
  тарифный план → операционная система (шаблон) → hostname → экран
  подтверждения с итоговыми параметрами. Пароль root, который UpCloud
  генерирует при создании, показывается один раз сразу после успешного
  создания сервера и больше нигде не хранится и не логируется. Автоматически
  подбирается правильный тип диска под план: дешёвые план­ы `DEV-*` умеют
  работать только с обычным ("standard") диском, а не с быстрым ("maxiops")
  — раньше это приводило к ошибке при создании сервера на таком плане, теперь
  бот сам выбирает подходящий тип;
- **списки зон/планов/ОС показываются постранично** — по 10 вариантов на
  экран с кнопками ◀️/▶️, вместо одного длинного списка (у UpCloud десятки
  планов и шаблонов ОС — раньше показывались все сразу, что было неудобно и
  для части шаблонов даже обрезалось);
- **смена тарифного плана** сервера (⚙️ Изменить план на карточке сервера)
  — бот показывает список доступных планов (тоже постранично) и подтверждение
  перед сменой; если сервер запущен, бот сначала попросит его выключить —
  это требование самого API UpCloud, не бота;
- **диски (💾 Диски)** — список дисков сервера, добавление нового диска
  (создаётся и подключается сразу), изменение размера (только в бо́льшую
  сторону — как и позволяет API), отключение диска от сервера и полное
  удаление;
- **бэкапы диска (📋 Бэкапы)** — создание бэкапа диска вручную, список
  существующих бэкапов, восстановление диска из бэкапа (перезаписывает
  текущее содержимое — требует явного подтверждения) и удаление бэкапа;
- **IP-адреса (🌐 IP-адреса)** — список публичных IP сервера, добавление
  нового публичного IPv4 и удаление существующего. У UpCloud IP-адрес
  привязывается к серверу уже при создании (в отличие от AWS/Azure elastic
  IP его нельзя "отвязать и привязать к другому серверу" — только удалить
  и создать заново на нужном сервере);
- **отключение аккаунта от бота** (сами сервера в облаке при этом не
  трогаются — это просто убирает сохранённые учётные данные).

Как и в разделе Panel, HTTP-клиент к UpCloud API (`bot/services/upcloud_api.py`)
переиспользует общий подход: любое изменение сервера/диска отправляет
только изменившиеся поля, ничего лишнего не перезаписывается — это
явно проверено тестами (сосед по диску не трогается при апгрейде плана,
второй диск не трогается при изменении размера первого и т.д.). Списки
дисков, бэкапов и IP адресуются по позиции в свежем списке с сервера
(как и хосты/инбаунды/клиенты панелей в разделе Panel) — данные никогда
не устаревают в состоянии бота, а сами колбэки остаются короткими.
Подключённые аккаунты хранятся в `data/cloud_accounts.json` (список
записей на пользователя, тот же принцип, что и `panel_connections.json`).

## Раздел Arsi WhoIs — инфо об IP и доменах

В главном меню → **🌐 Arsi WhoIs** бот просит прислать IP-адрес или домен и
в ответ присылает максимально подробную карточку в фирменном стиле ARSI —
никаких заглушек, данные берутся из реальных публичных источников в момент
запроса:

- **Для IP-адреса** (через [ipwho.is](https://ipwho.is)): страна и город
  (с флагом), провайдер (ISP) и, если регистрационная организация той же
  IP-подсети отличается от провайдера (частый случай для VPS — реселлер
  vs. настоящий дата-центр), отдельной строкой ещё и она, ASN, часовой
  пояс, обратный DNS (host), а также признаки **Proxy / VPN / Tor /
  Hosting** и отдельно — принадлежность к **Cloudflare** (по ASN и по
  имени провайдера/организации). Дополнительно бот запрашивает и живой
  RDAP-ответ настоящего регионального реестра (RIPE/ARIN/APNIC/...) —
  это официальные данные о том, кому реально выделен этот блок IP, а не
  догадка гео-IP базы, и когда реестр знает имя сети (netname) — оно
  показывается отдельной строкой «Сеть (реестр)»;
- **Для домена**: регистратор, дата регистрации/истечения/обновления,
  статус, серверы имён (с меткой, использует ли домен Cloudflare NS),
  DNS-записи **A / MX / TXT**, и — если домен резолвится — те же
  подробные геоданные по его IP, что и при прямом IP-запросе (страна,
  провайдер, ASN, Cloudflare). Данные о регистрации берутся сначала через
  RDAP ([rdap.org](https://rdap.org)), а если у зоны нет RDAP-сервера
  (например, у `.ru`) — бот сам находит нужный whois-сервер через IANA и
  делает классический whois-запрос по протоколу порта 43, как обычный
  `whois`-клиент. Ошибка показывается только если вообще ничего не
  нашлось — ни через RDAP, ни через классический whois, ни через DNS.

Карточка оформлена обычным текстом с жирными подписями полей и своим
эмодзи на каждую строку; моноширинным (`<code>`) остаётся только сам
IP/домен и прочие серверные идентификаторы (host, ASN, серверы имён,
DNS A/MX/TXT) — в едином фирменном стиле ARSI, без ссылок на сторонние
сервисы в самом тексте. Если у домена
есть резолвящийся IP, в конце карточки добавляется его полный блок
геоданных — те же поля, что и при прямом IP-запросе (страна, город,
провайдер, часовой пояс, Proxy/VPN/Tor/Hosting/Cloudflare), а не только
страна и провайдер вкратце. Ответ отправляется именно как
**реплай на сообщение с запросом** — Telegram сам показывает сверху
цитату исходного IP/домена, поэтому дублировать его в тексте карточки не
нужно. Ввод принимается в любом виде (ссылку с `http(s)://` и путём бот
сам сведёт к голому домену/IP).

## Тексты и премиум-эмодзи

Все тексты бота собраны в `bot/texts/` (`translations.py` — переводы всех
трёх языков, `main.py` — общие разделы, `node.py` — раздел Node) в едином
компактном стиле: заголовок с эмодзи → короткое пояснение курсивом → суть
одной-двумя строками.

Эмодзи не разбросаны по коду, а собраны в одном файле —
`bot/texts/premium_emoji.py`. Как подключить свои премиум-эмодзи:

1. Перешлите нужный эмодзи в чат с ботом `@itisemojibot` — он пришлёт
   `custom_emoji_id` (длинная цифровая строка).
2. Впишите его в словарь `IDS` в `bot/texts/premium_emoji.py`, например:
   `"welcome": "5368324170671202286"`.
3. Пока значение пустое (`""`), используется обычный эмодзи-заглушка —
   ничего не сломается, если руки дойдут не сразу.

Над каждой строкой словаря есть комментарий с одним словом — под каким
текстом стоит этот эмодзи (`welcome` — шапка `/start`, `node` — раздел
Node, `marzban`/`pasarguard` — заголовки нод, `success`/`error`/`warning` —
статусы установки, и т.д.).

⚠️ Важно: премиум-эмодзи работают только в тексте сообщений. В подписях
кнопок (`bot/keyboards/*.py`) Telegram не даёт использовать премиум-эмодзи —
там всегда обычные юникод-эмодзи.

## 2. Установка на сервер (VPS) через Docker — рекомендуемый способ

Это самый простой вариант: не нужно вручную ставить Python и зависимости,
а повторная установка/обновление — это одна команда. Подходит, чтобы
тестировать бота каждый раз после внесения изменений.

### Первый запуск на чистом сервере

Подключитесь к серверу по SSH (Ubuntu/Debian) и выполните:

```bash
curl -fsSL https://raw.githubusercontent.com/k9032431-cmd/Vpn_Bot/claude/arsicloudbot-menu-setup-ueqrl6/deploy.sh | bash
```

Скрипт сам:
1. установит Docker и Docker Compose, если их нет;
2. склонирует репозиторий в `~/arsicloudbot`;
3. создаст файл `.env` из примера и попросит вписать в него `BOT_TOKEN`;
4. соберёт образ и запустит бота в фоне (`restart: unless-stopped`, то есть
   бот сам поднимется после перезагрузки сервера).

Если предпочитаете руками — то же самое пошагово:

```bash
git clone --branch claude/arsicloudbot-menu-setup-ueqrl6 \
  https://github.com/k9032431-cmd/Vpn_Bot.git ~/arsicloudbot
cd ~/arsicloudbot
cp .env.example .env
nano .env               # вписать BOT_TOKEN
docker compose up -d --build
```

Проверить, что бот работает:

```bash
cd ~/arsicloudbot
docker compose logs -f
```

Напишите боту `/start` в Telegram — должно прийти приветствие с меню.

### Повторная установка / обновление после изменений в коде

Когда вы что-то поменяли в боте и запушили в GitHub, на сервере достаточно
одной команды:

```bash
cd ~/arsicloudbot
./update.sh
```

Скрипт подтянет последние изменения из текущей ветки (`git fetch` +
`git reset --hard`) и пересоберёт/перезапустит контейнер. Так можно
тестировать сколько угодно раз — старая версия каждый раз полностью
заменяется новой, никакого "мусора" не остаётся.

Если нужно снести и поставить полностью с нуля — просто удалите папку и
повторите команду установки из первого запуска:

```bash
rm -rf ~/arsicloudbot
curl -fsSL https://raw.githubusercontent.com/k9032431-cmd/Vpn_Bot/claude/arsicloudbot-menu-setup-ueqrl6/deploy.sh | bash
```

### Полезные команды Docker

```bash
docker compose ps              # статус контейнера
docker compose logs -f         # логи в реальном времени
docker compose restart         # перезапуск без пересборки
docker compose down            # остановить и удалить контейнер
```

## Переменные окружения

|---------------------------|--------------------------------------------------------------------|
